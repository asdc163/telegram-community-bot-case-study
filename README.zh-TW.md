## 要解決什麼

成員應該在原本聊天的群組完成參與，敏感設定由群主在私訊處理。流程還需要面對舊選單、群主變更、重複更新與發送失敗，避免把「能參與」和「能管理」混在一起。

## 我的工作

參與產品與操作流程、TypeScript 服務、角色權限、持久化投遞、規則式群管、回歸驗證與轉移包整理。使用 Node.js、TypeScript、Fastify、PostgreSQL 和 Docker。

## 幾個有影響的決定

一般成員的活動參與留在群內。群主在私訊選擇自己的群，設定與管理操作重新向 Telegram 查核當下角色；即使握有舊按鈕，失去群主身分後也不能繼續控制。

發送失敗要分辨限流、明確失敗和結果不明。限流可以延期，但結果不明就直接重送，可能讓同一則訊息出現兩次，因此要保留人工確認的狀態。

群管規則同時看角色和訊息來源。看起來像自家 Bot 的名稱或按鈕，不足以證明可信。Bot 仍受 Telegram 權限和可收到的訊息範圍限制。

交接時先停止舊服務，再驗證資料還原，並分別核對平台與應用程式的擁有權。加密資料的解密材料需要私下安全移交，不能因為搬機就換掉。

## 交付與驗證範圍

私有紀錄包含自動回歸、Telegram API 角色檢查、部分真人 Telegram 操作與轉移包驗證。較後期的行為調整，有些沒有重新完成客戶端點擊；不同證據層分開記載於 [驗證範圍](docs/verification.md)。
